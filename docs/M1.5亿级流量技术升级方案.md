# M1.5 亿级流量技术升级方案（对齐 GitHub 标杆）

> 日期：2026-09-19 ｜ 依据：对标 macrozheng/mall(84.8k★)、qiurunze123/miaosha(26.6k★)、YunaiV/yudao-cloud(19.5k★)、mall-swarm(13.1k★)
> 标杆选型原文件：docs/references/*.md ｜ 检索清单：docs/github_reference_projects.json

## 一、差距结论

M1 已有：MySQL 乐观锁防超卖、订单状态机 CAS、支付回调幂等、Redis 缓存旁路、雪花 ID、JWT。
**缺的「亿级流量核心逻辑」（本次 M1.5 补齐）**：

| # | 能力 | 标杆做法 | 我们的落地 |
|---|---|---|---|
| 1 | 异步削峰下单 | mall 用 RabbitMQ 解耦下单链路 | spring-boot-starter-amqp：下单主链路只做「Lua 预扣+发消息」，订单落库移到消费者匀速处理（WSL RabbitMQ） |
| 2 | 原子预扣+分桶 | miaosha：Redis+Lua 原子扣减 | seckill 秒杀链路：Lua 脚本「判限购+扣减」一步原子；热点商品库存 10 桶哈希分散，单 key 热点消除 |
| 3 | 多级缓存 | mall：Redis+本地缓存组合 | Caffeine(进程内 L1, 5s 短窗) → Redis(L2) → DB，读 QPS 大幅卸载 DB |
| 4 | 限流+幂等组件 | miaosha：令牌桶+接口幂等 | 自研 @RateLimit 注解（Redis+Lua 滑动窗口，对标 Sentinel 单机限流思路）+ @Idempotent 注解（token+setnx）；分布式锁升级 Redisson |

维持文档规划（M2/M3 范围，不在单机期硬上）：ES 搜索、MongoDB 评价、ShardingSphere 分库分表、Sentinel/Seata/Nacos 微服务化、K8s。
理由：单机 Windows 资源有限；但架构演进路径已写入总方案，M2 拆分时逐个引入。

## 二、M1.5 新增依赖（全部由 Spring Boot BOM 或阿里云镜像托管，零版本风险）

- spring-boot-starter-amqp（RabbitMQ）
- spring-boot-starter-cache + com.github.ben-manes.caffeine:caffeine（Boot 管理版本）
- org.redisson:redisson-spring-boot-starter:3.30.0

限流采用自研注解而非直接引 Sentinel：单机部署 Sentinel 控制台成本高、SCA 与 Boot 3.5 版本匹配存在不确定性；滑动窗口 Lua 自实现是 Sentinel 的同源思路（面试可讲「我会用 Sentinel，也懂它的底层实现」），M2 微服务化时按 mall-swarm 模式接入 SCA 全家桶。

## 三、升级后的下单链路（秒杀视角全图）

```
请求 → @RateLimit 限流(滑动窗口) → @Idempotent 幂等(token setnx)
     → Redis Lua [判限购+扣分桶库存] 原子执行
     → RabbitMQ(事务性: 先扣减成功才发消息; 消费失败回补库存)
     → OrderConsumer 匀速消费: 订单+明细落库(快照) → 返回下单受理
读链路: Caffeine(5s) → Redis(30min) → DB
兜底: 消费失败/超时未消费 → 延迟检查回补库存（M2 换事务消息+延迟消息）
```

## 四、验收标准（不达标继续修）

1. 冒烟全链路 11 步全部通过（注册→…→重复回调幂等）
2. 新增秒杀冒烟：限流生效(429)、幂等生效、分桶扣减正确、MQ 消费落库、Redis-DB 库存终态一致
3. 基线压测产出对比数据：同步下单 vs MQ 异步下单 QPS/P99，多级缓存命中后详情接口 QPS 提升
4. 全程零超卖（成功单数 ≤ 初始库存，分桶合计守恒）
