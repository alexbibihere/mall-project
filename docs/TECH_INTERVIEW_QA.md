# 技术点 × 面试题全景对照表

> 口径：左边是本项目**真实用到**的技术，右边是该技术面试官最常问的问题 + 本项目标准答案要点。
> 标注：【本项目】= 有真代码可展示；【实测】= 有压测/验证数据；【roadmap】= 诚实说没做但知道方向。

## 一、Java 基础与并发

| 技术 | 高频面试题 | 本项目答案要点 |
|---|---|---|
| **虚拟线程**【本项目】【实测】 | 虚拟线程是什么？和线程池的区别？什么时候用？ | JDK 21 载体线程挂载，I/O 阻塞时自动让出；product 读链路开启（I/O 密集收益最大）；CPU 密集不适合；对比：传统池 200 线程扛 200 并发，虚拟线程百万级挂起 |
| **线程池** | 参数怎么定？拒绝策略？ | 虚拟线程场景下业务线程池弱化，但 Tomcat/连接池仍需：IO 密集 `核心×2~4` 或按 RT 目标反推；压测时观察到 Hikari 池不足会先于 CPU 打满成为瓶颈 |
| **synchronized/锁** | 秒杀里怎么防并发？ | 不用 JVM 锁——分布式下失效；用 Redis Lua 单线程原子性替代，DB 乐观锁兜底 |
| **CAS/ABA** | 订单并发怎么处理？ | 状态机 `UPDATE ... WHERE status=#{from}`，影响行数=0 即冲突；实测：并发支付 vs 关单只有一方胜出 |

## 二、Spring / Spring Boot

| 技术 | 高频面试题 | 本项目答案要点 |
|---|---|---|
| **IOC/AOP** | 项目里哪里用了 AOP？ | 限流切面 `@RateLimit`（Redis+Lua 滑窗，注解在秒杀接口 5次/s/用户）、幂等切面 `@Idempotent`（token+setnx） |
| **Bean 生命周期** | 循环依赖怎么解决？ | 三级缓存；本项目 Feign 懒加载代理，未手写循环依赖场景，但能讲清 singletonObjects→earlySingletonObjects→singletonFactories |
| **事务失效** | 哪些场景事务失效？ | 亲自踩过：① 同类内方法自调用不走代理 ② 异常被 catch 吞掉 ③ 非 public。下单主链路 `@Transactional` + `afterCommit` 发 MQ 就是"事务提交后动作"标准用法 |
| **@Transactional 传播** | 事务提交后再发消息怎么保证？ | `TransactionSynchronizationManager.registerSynchronization` 的 `afterCommit`——本地消息表方案核心，防"事务回滚了消息却发出去了" |

## 三、Spring Cloud 微服务

| 技术 | 高频面试题 | 本项目答案要点 |
|---|---|---|
| **Nacos** | 注册中心原理？CP 还是 AP？ | 临时实例 AP（Distro 协议，心跳续约），持久实例 CP（Raft）；本项目 7 服务临时实例，60s 不健康剔除；亲历：服务假活时 Nacos 还有旧实例 → 网关 503 窗口 |
| **Gateway** | 网关做了什么？和 Nginx 区别？ | JWT 校验（全局过滤器）、白名单放行、路径路由 lb://负载均衡；Nginx 是四/七层流量入口，Gateway 是业务网关（鉴权/限流/灰度） |
| **OpenFeign** | 原理？超时怎么配？ | 动态代理 + LoadBalancer 客户端负载；本项目 4 条链路（order→product/user、seckill→product、search→product）；踩坑：缺 `@EnableFeignClients`/`loadbalancer` 依赖直接启动失败 |
| **服务雪崩** | 怎么防？ | ① 弱依赖降级 ② 超时短配快速失败 ③ 限流前置在网关；本项目把内部接口 `/internal/**` 与公开路由隔离 |

## 四、Redis（重灾区）

| 技术 | 高频面试题 | 本项目答案要点 |
|---|---|---|
| **Lua 原子扣减**【本项目】 | 为什么用 Lua？ | "查库存→判限购→扣减→记录用户"多步操作在 Redis 单线程内一次性执行，杜绝查了再扣竞态；`seckill_deduct.lua`：KEYS=分桶+用户集合 |
| **缓存穿透/击穿/雪崩** | 三件套怎么防？ | 穿透：不存在商品缓存 60s 空值；击穿：热点用本地 Caffeine 兜底（95%+ 命中）+逻辑过期思路；雪崩：TTL 加随机抖动；【roadmap】布隆过滤器 |
| **缓存一致性** | 先删缓存还是先更新 DB？ | 先更 DB 再删缓存（Cache-Aside）；商品变更走 MQ 事件；一致性靠 TTL 收敛——强一致缓存是伪需求，关键是窗口可控 |
| **分布式锁** | 用过吗？ | 超时关单用 Redisson 看门狗锁（自动续期，替代手写 setnx+TTL）；`lock:order:close:{orderNo}` 不等待抢锁，抢不到说明有人在处理 |
| **大 key/热 key** | 怎么处理？ | 大 key：购物车分 field 存；热 key：库存分桶 10 桶摊写压力 + 本地缓存挡读 |
| **Redis 持久化** | RDB 还是 AOF？ | Docker 单机 RDB（缓存场景可容忍丢）；若做库存真源需 AOF everysec + 主从 |
| **Redis 为什么快** | 单线程为什么快？ | 内存 + IO多路复用 + 单线程无锁竞争；6.0 网络 IO 多线程但命令执行仍单线程——这正是 Lua 能保证原子的基础 |

## 五、消息队列（RocketMQ）

| 技术 | 高频面试题 | 本项目答案要点 |
|---|---|---|
| **本地消息表**【本项目】 | 消息怎么保证不丢？ | ① 任务表与订单同事务落库（先于发送持久化）② afterCommit 发送，失败靠补偿 ③ 补偿任务 10s 重扫 INIT/PROCESSING 滞留 ④ 对账任务 5 分钟终局校验 |
| **消息重复** | 怎么幂等？ | 消费端 CAS 抢任务 `WHERE status IN('INIT','FAILED')`——抢不到直接 skip；DB 乐观锁二次兜底；秒杀消费端 orderNo 查重 |
| **消息顺序** | 需要顺序吗？怎么保证？ | 本项目扣减任务无顺序依赖（不同 SKU 行独立）；同订单行靠 CAS + 终态不可逆保证正确性；若需顺序用 MessageQueueSelector 同单同队列 |
| **事务消息 vs 本地消息表** | 对比？ | 事务消息：半消息+回查，无本地表但依赖 MQ 特性；本地消息表：业务库强一致、通用但要自己扫表。本项目主链路用本地消息表（可完全自证），讲得出两者取舍 |
| **消息堆积** | 堆积了怎么办？ | 消费端无重逻辑可水平扩消费者；堆积告警指标看 consumer lag；本项目补偿任务实际就是"堆积自愈"——实测：压测 30 任务秒级消化 |
| **延迟消息** | 超时关单怎么做？ | 【roadmap 升级项】当前定时扫描（30s + Redisson 锁），M2 计划换 RocketMQ 延迟级别；两种都讲得出：延迟消息省扫描、扫描版可控性强 |

## 六、分布式事务（最有故事的一节）

| 方案 | 高频面试题 | 本项目答案要点 |
|---|---|---|
| **Seata AT**【实测后弃用】 | AT 原理？为什么弃用？ | 一阶段本地提交+undo_log 镜像，二阶段 TC 驱动 commit/rollback；**弃用原因（实测）：每单分支注册×4+镜像写×4+TC 往返×3 → 下单 QPS 167.6→22.5（-86.6%）**；还有全局锁行竞争 |
| **本地消息表**【本项目主方案】 | 为什么它是主方案？ | 与订单同事务=强一致起点，之后全部异步最终一致；一致性成本从"链路"挪到"对账"，吞吐最高；对账 drift=0 验证 |
| **TCC** | 为什么不用？ | Try/Confirm/Cancel 三段侵入太强，每个参与方都要写；适合资金类强一致场景；能讲但没实现——诚实 |
| **2PC/3PC** | 了解吗？ | 能讲原理与同步阻塞/协调者单点缺陷；正因这些缺陷，业界才走向"柔性事务"（AT/TCC/SAGA/本地消息表） |
| ** Saga** | 知道吗？ | 长事务拆本地事务序列+逆向补偿；本项目手写补偿循环(M2.1)就是 Saga 雏形，后来被消息表替代 |

## 七、MySQL

| 技术 | 高频面试题 | 本项目答案要点 |
|---|---|---|
| **乐观锁**【本项目】 | 为什么不用悲观锁？ | `WHERE stock>=?` 影响行数判断，无锁等待；秒杀冲突率高时悲观锁串行化反而稳，但 Redis 前置已把 DB 冲突降到极低 |
| **索引** | 索引失效场景？分表后索引怎么建？ | 分表后各分表独立索引；order_no/user_id 分片键必带；讲得出：最左前缀、隐式转换、函数计算失效 |
| **事务隔离级别** | RR 下的幻读？ | 能讲 MVCC（ReadView+undo 版本链）与当前读间隙锁；本项目热点都在 Redis，DB 事务短小 |
| **分库分表**【本项目】 | 怎么拆？跨片查询怎么办？ | user_id 哈希 2×2（演示规模，方法论支持 16×64）；**基因法**：订单号末位嵌 uid%10 → buyer/订单号同片免路由；seller 维度→异构索引表（roadmap） |
| **ShardingSphere**【本项目】 | 踩过什么坑？ | 真实三连：① 5.4→5.5 坐标改名 shardingsphere-jdbc-core→shardingsphere-jdbc ② YAML 引擎 snakeyaml 1.x 与 Boot 2.x 冲突→改编程式配置 ③ 5.5 单表严格校验需 ds0. 前缀显式注册；还补了缺失的 reactor-core 传递依赖 |
| **主从/读写分离** | 做了吗？ | 【roadmap】方法论能讲：半同步复制+读库路由+主从延迟处理（关键读走主库） |

## 八、Elasticsearch

## 九、分布式理论与架构设计

| 主题 | 高频面试题 | 本项目答案要点 |
|---|---|---|
| **CAP/BASE** | 你的系统选 CP 还是 AP？ | 注册发现 AP（可用优先），交易一致性用"BASE：基本可用+软状态+最终一致"；对账保证收敛 |
| **幂等** | 全链路哪里做了幂等？ | 支付回调（支付单 CAS+金额校验）、秒杀（token 令牌一次性+一人一单 SISMEMBER）、扣减任务（CAS 抢占）——三种不同实现对应三种场景 |
| **限流算法** | 令牌桶/漏桶/滑窗对比？你用哪个？ | Redis+Lua 滑动窗口（实现简单且平滑）；网关全局限流+用户级 ParamFlow 语义双层；压测实测限流拦截 167/500 请求 |
| **分布式 ID** | 雪花时钟回拨怎么办？ | 自实现：小幅回拨等待，大幅拒绝+告警；**基因法扩展**：订单号末位嵌 uid%10——这是本项目分片路由的基石 |
| **对账** | 为什么需要对账？ | 最终一致的"最终"要有人兜底：实时对账（任务终态校验）+ T+1 思想（资金对账 roadmap）；实测 drift=0，且首跑就抓出分片键漏设 bug |
| **分布式锁** | Redisson 原理？ | 看门狗自动续期（默认 30s/10s 续），Lua 原子加解锁；超时关单实战使用 |

## 十一、三分钟自述模板（背下来）

**开场**：项目定位一句话 + 数字弹药。

**主体（挑 2~3 个深讲，按面试官反应切换）**：
1. **架构演进线**：单体 167 QPS 基线 → 拆 7 服务 → AT 实测 -86.6% → 弃强一致改本地消息表 → 对账 drift=0。突出"每个决策有数据"。
2. **秒杀全链路**：令牌防重放 → 滑窗限流 → Lua 分桶原子预扣 → MQ 异步落库 → CAS 幂等消费 → 对账收敛。突出"三层防超卖+实测零超卖"。
3. **分库分表**：基因法设计动机（免跨片）→ ShardingSphere 三版本迁移踩坑 → item 分片键冗余。突出"工程落地细节"。

**收尾**："方法论同源京东，体量虽小但每个原则都被我亲手验证过为什么成立、代价是多少——您任意挑组件往下钻。"
