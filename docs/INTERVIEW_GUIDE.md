# 面试叙事手册 —— 讲清楚架构、逻辑与理念

> 用途：面试前 30 分钟通读。按「总 → 分 → 深」顺序：先一句话定位，再架构分层，再八大设计理念，最后高频追问弹药库。

---

## 一、一句话定位（开场 30 秒）

> "这是一个类京东架构的亿级流量商城，我从单体开始，亲手走完了**微服务化 → 分布式化**的完整演进。它的特殊之处在于：每一个高并发技术点——缓存、削峰、防超卖、最终一致、分库分表——都不是照搬八股，而是**有真代码、有压测数据、有冒烟验证**。比如我用实测证明 Seata AT 让下单吞吐掉了 86%，这正是京东骨干链路选择最终一致的量化原因。"

**数字弹药**（随手可用）：7 微服务 · 16 步冒烟全绿 · 热读 3036 QPS / P99 47.6ms · 秒杀受理 89.1 TPS · 零超卖 · 分片路由 3/3 ✓ · 对账 drift=0

## 二、整体结构（一张图讲明白）

```
客户端
  ↓
Gateway :9000（JWT 鉴权 · 白名单 · Redis+Lua 限流）
  ↓ 路由
6 大业务服务（Nacos 注册发现，Feign 同步调用，X-User-Id 透传）
  user:8101    product:8112    cart:8113
  order:8104   seckill:8105    search:8106
  ↓
中间件层
  Redis(缓存/Lua/幂等) · RocketMQ(削峰/事件) · ES(搜索) · Nacos(注册)
  ↓
数据层
  ShardingSphere 5.5.2 → MySQL ds0(mall) + ds1(mall_shard1)
  2 库 × 2 表，基因法路由
  ↓

```

**分层职责一句话**：网关管入口安全，服务管业务，中间件管解耦与加速，数据层管容量，对账管最终正确。

## 三、八大设计理念（核心！每条都是"问题→方案→验证"结构）

### 理念 1：读多写少 → 多级缓存漏斗
- **问题**：商品详情读 QPS 远超 DB 承受
- **方案**：Caffeine 本地 → Redis → DB，逐层兜底；空值缓存 60s 防穿透
- **验证**：热点命中本地缓存 95%+，实测热读 3036 QPS / P99 47.6ms / 0 失败

### 理念 2：写高峰 → 异步化削峰
- **问题**：秒杀瞬时流量远超 DB 写能力
- **方案**：受理只做「Lua 预扣 + 发 MQ」，落库全异步；主链路与 DB 解耦
- **验证**：受理 89.1 TPS（P99 116ms），DB 在受理期间零压力

### 理念 3：防超卖 → 两层防线
- **第一层**：Redis Lua 原子「查库存+判限购+扣减」——杜绝查了再扣的竞态
- **第二层**：DB 乐观锁 `WHERE stock >= ?` 兜底
- **验证**：受理 30 = Redis 消耗 30 = DB 消耗 30，历史所有压测零超卖

### 理念 4：热点 key → 库存分桶
- **问题**：单 key 热点打满单节点 Redis
- **方案**：100 件拆 10 桶，请求 hash 路由并行扣减
- **讲点**：分桶数 = 峰值 QPS / 单 key 承受上限

### 理念 5：分布式事务 → 最终一致（本项目最有含金量的决策）
- **演进路径**：手写补偿(M2.1) → Seata AT(M2.2) → **本地消息表(M3.1)**
- **决策依据**：实测 AT 使下单 QPS 167.6→22.5（-86.6%），归因 = 全局锁 + undo_log 镜像 + TC 三次往返
- **新方案**：订单+任务表同事务落库 → afterCommit 发 MQ → CAS 抢任务幂等扣减 → 补偿任务 10s 重扫 → 消息不丢不重
- **升华**："这就是京东骨干链路不用 AT 的量化原因——一致性靠兜底，不靠链路"

### 理念 6：数据正确性 → 三道防线
1. **事前**：CAS 状态机（并发支付/取消只有一方胜出）+ 支付回调三重校验（幂等→金额→状态）
2. **事中**：库存不足时等兄弟任务终态 → 只回补已 DONE 行（防超补）
3. **事后**：对账中心每 5 分钟闭环——订单三态校验、滞留任务重发、PAID 非 DONE 资损告警、库存 Redis↔DB 比对（实测 drift=0）

### 理念 7：海量数据 → 分库分表 + 基因法
- **方案**：2 库 × 2 表，orders 按 user_id 路由；**订单号末位嵌 user_id%10 基因**——按订单号查与按买家查天然同片，免跨片
- **踩坑可讲**：ShardingSphere 5.4→5.5 坐标改名、snakeyaml 与 Boot 冲突改编程式配置、单表严格校验——三个版本 API 迁移全趟过
- **验证**：新单路由 3/3 正确，item 行冗余 user_id 与订单同片

### 理念 8：搜索 → 事件驱动同步
- **链路**：商品变更 → 事务提交后发 MQ → search 消费 upsert ES；启动全量 reindex + /internal/reindex 对账兜底
- **讲点**：MQ 异步 vs Canal binlog 两条路线的取舍（我们 MQ 先行，Canal 是防漏发的增强项）

## 四、演进故事线（应对"为什么这么设计"）

| 阶段 | 遇到的问题 | 决策 | 代价/收益 |
|---|---|---|---|
| M1 单体 | 能跑但撑不住量 | 先跑通，压测留基线 167.6 QPS | — |
| M2.1 拆服务 | 单体耦合、无法独立扩容 | Nacos+Gateway+Feign 拆 7 服务 | 引入网络跳数 |
| M2.2 强一致 | 跨服务扣库存怎么保证正确 | Seata AT 试点 | **实测 -86.6%** |
| M3.1 弃 AT | 吞吐代价不可接受 | 本地消息表最终一致 | 吞吐回升，复杂度转移到补偿+对账 |
| M3.2 分库分表 | 单表容量天花板 | 基因法 2×2 | 查询维度受限→基因闭环解决 |
| M3.3 对账 | 最终一致"最终"有多可靠 | 定时闭环对账 | 实测 drift=0，还抓出分片键漏设 bug |

**万能收尾句**："每个决策我都先用数据证明了问题存在，再验证方案有效——架构选型不是背出来的，是测出来的。"

## 五、高频追问弹药库

**Q: 消息丢了怎么办？**
三层：① 本地消息表与订单同事务（发送前已持久化）② 发送失败/消费中断由补偿任务 10s 重扫重发 ③ 对账任务 5 分钟再兜底 + PAID 单异常告警。

**Q: 消息重复消费怎么办？**
消费端 CAS 抢任务（UPDATE ... WHERE status IN ('INIT','FAILED')），抢不到=已被处理，天然幂等；DB 层乐观锁二次兜底。

**Q: 为什么不用 Seata TCC？**
TCC 要每个参与方写 Try/Confirm/Cancel 三段逻辑，侵入性强；AT 无侵入但全局锁代价实测 -86.6%。本地消息表把一致性成本从"链路"挪到"对账"，吞吐最高。三者都能讲，有实测数据的是 AT vs 消息表。

**Q: 分库分表后 seller 维度怎么查？**
基因法只闭环 buyer 和订单号维度；seller 维度走异构索引表（冗余 seller_id→order_no 映射）或 ES 宽表——这是标准 answer，异构表在 roadmap 里。

**Q: 分桶后某桶先卖完怎么办？**
hash 路由到售罄桶时顺延下一桶；全售罄回 DB 兜底池。桶间不平衡靠再平衡任务（roadmap）。

**Q: 缓存一致性怎么保证？**
先更 DB 再删缓存（Cache-Aside）；商品变更走 MQ 事件驱动删除/更新；容忍短暂不一致由读链路 TTL 收敛——强一致缓存本身是伪需求，关键是不一致窗口可控。

**Q: 你这项目QPS才几千，凭什么讲亿级？**
"方法论同源、体量不同。我用开源件在代码级验证了每条原则**为什么成立、代价是多少**——比如 AT 的 -86.6% 就是我自己测的。面试官您可以任意挑一个组件往下钻，我都能讲到实现层。"
