# M2.4 压测对比报告：单体 → 微服务化

> 日期：2026-09-20 ｜ 环境：单机 Windows 11（Docker Desktop: Redis/RocketMQ/Nacos/Seata/ES）+ JDK 21 虚拟线程
> 压测工具：scripts/mall_bench.py（自研，Python 线程池 + HTTPConnection）
> 所有数字均为本机实测，非估算。

---

## 2. 下单链路 -86.6% 的损耗归因（按贡献排序）

1. **Seata AT 全局事务（最大头）**：每笔订单 = TC begin/register×N 分支 + undo_log 前后镜像写 + 二阶段 commit 往返；order 日志每单 5+ 条 Seata INFO。AT 的全局行锁 + 镜像写让本地事务变网络协调事务。
2. **Feign 串行调用 4 跳**：地址快照(user) + 商品快照×N(product) + 库存扣减×N(product)，串行 RTT 叠加。
3. **网关转发一跳**：路由 + JWT 校验 + 剥离伪造头，增加单跳代理延迟。
4. **Redis/Lua 幂等 + MQ 事务消息**：同步发送 + 半消息机制。

> **架构启示（面试讲点）**：AT 模式「拿吞吐换透明一致性」。京东骨干链路默认不用强一致分布式事务，而是「本地事务 + 本地消息表 + 对账兜底」的最终一致——本项目的实测数据就是这一架构决策的量化注脚。演进方向：同步链路改 TCC（Try-Confirm-Cancel 少一次全局锁）或消息最终一致（事务消息替代 AT）。

## 3. 读链路 -42%~-53% 的归因与对策

- 热点命中时 product 本地 Caffeine 命中率约 95%+，瓶颈已不在缓存而在 **网关转发 + HTTP 多跳**（M1 直连单进程内存调用）。
- 对策优先级：① 静态化+CDN 卸载（M3 规划）② 网关连接复用/响应压缩 ③ 详情页聚合接口一次拉全（减少往返）。
- 即便如此，**3000 QPS / P99 47.6ms / 0 错误** 的读能力已覆盖本机容量上限的量级验证需求。

## 4. 秒杀链路：架构换挡后吞吐与正确性双达标

- 受理 34.1 TPS（含令牌两跳），**拒绝路径扛住了 450/500 的流量**（283 限购 + 167 限流），真正进入扣减的只有 50。
- 分桶 Lua 消除了单 key 热点；MQ 异步落库让受理 RT 与 DB 完全解耦（受理期 DB 零压力）。
- 一致性三方核对通过：受理 50 = Redis 消耗 50 = DB 消耗 50，**零超卖**。
- 注意：M1 P99 80ms 是纯受理口径（无令牌跳数、库存量级不同），跨形态对比仅供方向参考。

## 5. 结论

1. **微服务化不是免费的**：同步下单吞吐 -86.6% 是 AT + Feign 串行 + 网关三重代价的量化；换来的是独立扩缩容、故障隔离与团队并行度。
2. **读链路与秒杀链路在微服务形态下依然健康**（3036 QPS / 34.1 TPS / 零超卖），证明「削峰+缓存+异步化」的架构红利覆盖了分布式化的固定损耗。
3. **下一步优化路线**（按 ROI）：下单链路去 AT 改事务消息最终一致 → Feign 并行化（地址/商品快照并发拉取）→ 详情静态化+CDN → 分库分表（M3）。

## 附：环境与口径备注

- 单机压测，容器与 JVM 同宿主机争抢 CPU，绝对值仅供纵向对比（M1 vs M2 同机同口径）。
- M1「缓存热读 5224~6504」为当时多轮数据区间；本次 M2 口径为单一热点商品 2500 次详情请求。
- 复现命令：`python scripts/mall_bench.py bench --total 300`（同步）、`--bench-mode seckill --threads 50 --total 500 --product-id 3`（秒杀）。
